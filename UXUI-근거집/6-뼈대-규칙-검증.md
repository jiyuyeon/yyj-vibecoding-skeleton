# 뼈대 프롬프트 규칙 검증 (2026-11-24)

- 뼈대 프롬프트 v1.1의 화면 규칙을 근거와 대조한 결과
- 판정: 맞음은 그대로, 일부는 조건을 붙여 고침, 다름은 근거 쪽으로 고침

## 안내와 피드백

| 기존 규칙 | 판정 | 무엇이 다른지 | 출처 |
|---|---|---|---|
| 팁은 바깥 누름과 Esc로 닫는 팝오버로, 아코디언이나 늘 펼침은 쓰지 않음 | 일부 | 닫는 방식은 토글팁 기준과 맞음. 다만 결과를 좌우해 대부분이 알아야 하는 조건은 늘 보이게 두라는 것이 기준이고, 일부만 필요한 긴 도움말은 접힘(details)도 권장됨. 카본은 필수 정보를 토글팁에 넣지 말라고 함 | Carbon Toggletip, Inclusive Components, NN/g Tooltip Guidelines, NN/g Accordions on Desktop, GOV.UK Details |
| 저장 중이거나 AI 대기 중엔 영역을 흐리게, 스피너 + 지금 하는 일 한 줄 + 시간, 입력 막기(inert), 길면 취소와 Esc | 일부 | 한 줄 설명, 긴 대기의 취소는 맞음. 10초 넘으면 스피너 대신 차오르는 막대와 대략 남은 시간이 기준. 막는 범위는 바뀌는 영역으로 한정하고 나머지는 계속 쓰게(애플). inert는 시각 표시를 따로 해야 함(MDN). 2~10초에는 남은 시간까지 필요 없음 | NN/g Response Times, NN/g Progress Indicators, Apple Progress indicators, Apple Loading, MDN inert |
| 스켈레톤(천천히 밝아졌다 어두워지는 회색 막대) + 한 줄, 과정을 보여 주면 더 믿음 | 일부 | NN/g는 스켈레톤을 화면 전체 처음 불러오기, 10초 미만에 한정하고 단일 영역은 스피너를 권함. 움직임은 산만할 수 있다고 경고. 과정 노출 효과는 연구가 있으나 잰 것은 신뢰가 아니라 인지된 가치(Buell, Norton 2011). NN/g 스켈레톤 글은 신뢰 효과를 주장하지 않음 | NN/g Skeleton Screens 101, Buell, Norton The Labor Illusion, NN/g Visibility of System Status |
| 축하할 순간은 작은 창이 아니라 전체 화면으로 | 일부 | 긴 과정을 끝낸 순간은 전용 완료 화면이 기준과 맞음(GOV.UK). 하지만 일상적인 성공은 토스트나 제자리 표시가 기준이고, 애플은 중요한 완료만 확인하라고 함. 흐름 중간 단계 완료는 배너 정도 | GOV.UK Confirmation pages, GOV.UK Notification banner, Apple Feedback, Toss TDS Toast |
| 진행은 숫자 대신 차오르는 것으로 | 일부 | 막대가 숫자 시간보다 낫다는 점은 맞음(NN/g). 다만 NN/g는 막대에 설명 글과 단계 수(50개 중 3번째)나 대략 남은 시간을 함께 두라고 함. 숫자를 빼라는 기준은 아님 | NN/g Response Times, NN/g Progress Indicators, Apple Progress indicators |
| 처음 쓰는 사람에게 핵심 단추마다 코치마크 한 번씩 | 일부 | 한 번만, 하나씩은 맞음. 그러나 기준은 혼자 찾기 어려운 독특한 기능에만, 그 기능에 닿은 순간에 띄우기. 핵심 단추마다 첫 실행에 연달아 짚는 방식은 NN/g가 기억 부담과 어려워 보임을 이유로 피하라고 함. 이미 쓴 기능엔 띄우지 않음(애플) | NN/g Instructional Overlays, NN/g Onboarding Tutorials vs. Contextual Help, Apple Offering help |
| 브라우저 alert, confirm 대신 직접 디자인한 확인창 | 맞음 | MDN은 dialog 요소를 대안으로 들고, 결과를 말하는 단추 라벨(NN/g, 애플)은 기본 confirm에서 바꿀 수 없음(이 부분은 판단). 덧붙일 점: 되돌릴 수 있는 동작이면 확인창보다 실행취소를 먼저 고려 | MDN Window confirm(), NN/g Confirmation Dialogs, Apple Alerts |

## 입력과 고르기

| 기존 규칙 | 판정 | 근거와 달라지는 점 | 출처 |
|---|---|---|---|
| 스위치와 개수 같은 설정은 흩어진 카드가 아니라 줄로 나눈 묶음 목록 하나에 | 맞음 | 애플 묶음 목록과 "스위치는 목록 줄 안에서만", NN/g "같은 종류에는 카드보다 목록"과 일치 | Apple HIG Lists and tables, Toggles / NN/g Cards |
| 필수와 선택은 제목 옆 작은 표시로 | 맞음 (표시 방식은 엇갈림) | 이름 옆에 두는 것은 세 곳 모두 같다. 어떤 표시를 쓸지는 다르다: NN/g 필수 별표, 베이마드 필수 별표와 "(선택)" 둘 다, GOV.UK "(선택)"만 쓰고 별표 금지. 흐린 회색 표시는 피한다(NN/g) | NN/g Required Fields / Baymard Required and Optional / GOV.UK Question pages |
| 예시 입력은 입력칸 바로 아래에 | 일부 | "칸 밖에, 늘 보이게"는 맞다(NN/g, GOV.UK). 위치는 엇갈린다: GOV.UK는 이름과 칸 사이(칸 위), 토스 TDS는 칸 아래 도움말. 칸 안 안내 글에 예시만 두는 것은 GOV.UK가 금지, 베이마드는 짧은 형식 예시면 허용 | NN/g Placeholders / GOV.UK Text input / 토스 TDS TextField / Baymard Inline Labels |
| 주요 동작은 아래 고정, 스크롤로 사라지지 않게 | 일부 | 모바일 앱은 맞음(토스 FixedBottomCTA, 안드로이드 adjustResize로 버튼 막대를 키보드 위로). 조건: 고정 막대가 초점 받은 칸을 가리면 안 된다(WCAG 2.4.11). 웹 양식은 GOV.UK처럼 질문 바로 아래 일반 버튼이 표준이라 매체에 따라 다르다. 아래 고정이 낫다는 대조 연구는 찾지 못함 | 토스 BottomCTA / Android 입력기 표시 / W3C 2.4.11 / GOV.UK Question pages |
| 이름이 긴 모델 고르기는 세그먼트가 아니라 드롭다운(이름 왼쪽, 값 오른쪽, 설명 아래) | 일부 | 긴 이름에 세그먼트를 쓰지 않는 것은 맞다(애플: 짧은 명사, 비슷한 길이, 아이폰 5개까지). 그러나 선택지가 5개 이하이고 자리가 있으면 NN/g와 GOV.UK는 드롭다운보다 펼친 라디오 목록을 먼저 권한다. 애플 팝업 버튼은 목록 아래 설명 글을 허용한다. "이름 왼쪽, 값 오른쪽" 배치를 정한 문서는 찾지 못함 | Apple HIG Segmented controls, Pop-up buttons / NN/g Listboxes vs. Dropdown / GOV.UK Select |
| 어떤 옵션 때문에 못 쓰게 된 칸은 숨기지 말고 남겨서 흐리게, 이유 한 줄 | 일부 | 이유를 밝히라는 점은 맞다(NN/g). 다만 숨길지 흐릴지는 조건부: 있다는 걸 알아야 하면 흐리게, 지금 방식과 무관하면 숨김(스매싱 매거진). GOV.UK는 고른 답에 맞는 질문만 펼치는 방식(나머지는 숨김)을 쓴다 | NN/g 비활성 버튼 영상 / Smashing Hidden vs. Disabled / GOV.UK Radios |
| 여러 단계 입력: 번호 단계, 앞 단계를 끝내야 다음이 열림, 아래 버튼은 지금 할 동작 하나 | 맞음 | NN/g 마법사(단계 표시, 순서 강제, 뒤로 버튼), 토스 ProgressStepper(지금 단계, 끝난 단계 체크), 애플 "필요한 값을 넣어야 다음 버튼 활성". 덧붙일 점: 뒤로 가기를 분명히, 끝에 확인 화면(GOV.UK). 버튼 이름은 NN/g는 하는 일로, GOV.UK는 "Continue" 통일로 엇갈림 | NN/g Wizards / 토스 ProgressStepper / Apple Entering data / GOV.UK Check answers |
| 누름 영역 44px 이상 | 맞음 | 애플 44pt와 같다. 머티리얼은 48dp로 더 크고, WCAG 최소(AA)는 24px, 44px은 AAA | Apple HIG Buttons / Material Chip.md / W3C 2.5.8 |

## 화면 구조와 이동

| 기존 규칙 | 판정 | 근거와 보탤 점 |
|---|---|---|
| 바텀시트는 지금 화면을 보며 끝내는 짧은 입력이나 선택에만. 긴 읽기, 상세, 축하는 화면으로 | 맞음 | NN/g 바텀시트 글(2023-06-11)과 Apple Sheets(2026-03-24)가 같은 말을 한다. 축하 화면은 두 출처 모두 직접 다루지 않아 확인 못 함. M3는 긴 동작 목록을 모달 바텀시트에 넣고 안에서 스크롤하는 것을 허용해, 긴 목록 자체는 금지가 아니다(차이) |
| 버튼 하나로 끝나는 일은 시트 없이 그 자리에서 | 일부 | NN/g 모달 글(2017-04-23)이 단순한 선택은 인라인 요소를 대안으로 든다. 버튼 하나라는 기준까지 정한 출처는 없다 |
| 시트 위에 시트 금지 | 맞음 | Apple Sheets(한 번에 하나), NN/g 바텀시트(쌓지 말 것), Apple Popovers(팝오버 위 팝오버 금지) |
| 손잡이를 두고 실제로 동작하게 | 맞음, 보탤 점 있음 | M3는 손잡이를 끌기뿐 아니라 눌러서 높이를 바꾸거나 닫게 하라고 한다. NN/g는 손잡이만으로는 부족하니 닫기 버튼과 기기 뒤로 가기도 지원하라고 한다. Apple은 밀어서 닫기를 지원하되 저장 안 된 입력이 있으면 확인을 묻게 한다 |
| 개수가 적으면 가로, 많거나 늘면 세로, 보이는 것만 그리고 이어서 불러온다 | 맞음 | NN/g 모바일 캐러셀(끝까지 3~4번, 많으면 목록), NN/g 가로 스크롤(데스크톱 사용자 거부), M3 캐러셀(세로 전체 보기 필수), Baymard 더 보기 연구. 이어 불러올 때 뒤로 오면 보던 자리 유지가 함께 필요하다(Baymard, NN/g) |
| 긴 목록에는 분류 칩과 정렬, 최근순 기본, 고른 정렬 기억 | 일부 | 고른 정렬 기억은 GitLab, Baymard 493이 뒷받침한다. 최근순 기본은 근거 없음: Baymard는 한 기준만의 기본 정렬이 전체를 잘못 보이게 한다고 하고, GitLab은 화면마다 정하라고 한다. 내가 만든 것 모음처럼 시간이 기준인 목록이면 최근순이 맞고, 고르는 목록이면 다시 정해야 한다. 칩 자체를 권한 출처는 M3(세그먼트 6개 이상이면 칩) 정도다 |
| 여러 단계 구조에는 경로 표시, 앞 단계를 누르면 돌아감 | 맞음, 조건 있음 | NN/g 경로 글과 GOV.UK. 다만 1~2단계짜리 얕은 구조와 순서대로 가는 절차에는 쓰지 않는다. 경로는 방문 기록이 아니라 구조를 보여 주므로, 누르면 기록상 뒤로 가는 것이 아니라 그 단계 화면으로 간다. 모바일은 마지막 1~2단계만 |
| 기간 화면은 기간 라벨, 좌우 화살표, 좌우로 밀어 이동 | 맞음(간접 근거) | SAP 날짜 구간(화살표와 월, 연 표시), M3 날짜 고르기(화살표와 가로 밀기). 통계 같은 기간 화면 자체를 다룬 공식 지침은 찾지 못했다. 밀기만 두면 W3C 2.5.7(끌기 대안) 위반이 될 수 있어 화살표는 꼭 남긴다. M3는 탭 바 구역 사이 밀기를 금지하므로, 기간 밀기와 탭 이동 밀기가 겹치지 않게 한다 |
| 편집 동작(대표 지정, 삭제)은 편집 모드 뒤에 | 맞음, 차이 있음 | Apple 목록 지침(iOS는 편집 모드에서 고르기, 순서 바꾸기). NN/g는 밀어서 삭제도 허용하되 확인이나 되돌리기를 요구한다. 순서 바꾸기는 끌기 말고 버튼 대안 필요(W3C 2.5.7) |
| 넣기 전후 칸 높이 같게 | 맞음 | web.dev: 자리를 먼저 잡고, 크기 고정 칸 안에서 내용 교체, 비율 지정. 누른 직후 0.5초 안의 이동은 CLS에서 빠지지만, 그래도 눌린 자리가 밀리지 않는 편이 낫다(판단) |
| 툴팁은 최상단 층, 화면 밖이면 뒤집기 | 맞음(기술 문서 근거) | MDN 팝오버(최상단 층에서 모든 내용 위), MDN 앵커 위치 지정 대안(flip-block, flip-inline), Floating UI flip과 shift. NN/g는 관련 내용을 가리지 말라고만 하고 화면 끝 처리는 다루지 않는다. Apple은 좁은 폰 화면에서는 팝오버 대신 시트를 쓰라고 한다 |

## 편집 도구와 데이터

| 기존 규칙 | 판정 | 근거 |
|---|---|---|
| 편집 화면: 왼쪽 도구 막대, 세로 브러시 크기 슬라이더 + 단축키 + 끌기, 오른쪽 위 취소와 완료, 안내는 짧은 토스트, 맥락 버튼은 아래 가운데, 늘 보이는 안내 막대는 두지 않음 | 일부 | 세로 슬라이더는 프로크리에이트와 같아요(Procreate Interface). 단, 애플은 일반 슬라이더는 가로를 권해요(Apple HIG Sliders). 대괄호 단축키는 맞아요(Adobe Keys for Painting and Brushes). 끌어서 크기 바꾸기는 프로크리에이트 슬라이더 미세 조절만 확인했고, 포토샵의 보조키+끌기는 공식 문서로 확인 못 했어요. 취소와 완료는 애플 기준으로 취소가 왼쪽 위, 완료가 오른쪽 위라서 "둘 다 오른쪽 위"는 달라요(Apple HIG Sheets). 안내는 하나씩 그 순간에는 맞지만, 저절로 사라지는 토스트에만 담으면 안 되고 다른 곳에서도 찾을 수 있어야 해요(NN/g Instructional Overlays, Chrome Persistent toast). 맥락 버튼이 캔버스 위에 뜨는 것은 맞고(Adobe Contextual Task Bar), 피그마 도구 막대도 아래에 떠요(Figma UI3 blog). 정확히 "아래 가운데" 고정 위치인지는 포토샵 문서에서 확인 못 했어요. 왼쪽 도구 막대는 이번에 연 문서에서 위치를 글로 확인하지 못했어요. |
| 캔버스가 패널 전체를 차지하고 버튼은 그 위에 떠 있음 | 일부 | 작은 도구 막대를 띄우는 것은 맞아요. 하지만 피그마는 큰 패널까지 띄웠다가 캔버스가 가려지고 작업이 느려져 붙박이로 되돌렸어요(Figma UI3 blog, 2024-10-01). 큰 속성 패널은 붙이고 접을 수 있게, 작은 막대만 띄우는 쪽이 근거와 맞아요. |
| 같은 종류 도구의 기본 동작(되돌리기, 돌려 보기, 크기와 세기, 보기 모드, 단축키, 선택으로 할 수 있는 것: 이동, 자유 변형, 채우기)을 나열해 다 있는지 점검 | 맞음 | 프로크리에이트 선택 도구는 선택 뒤 칠하기, 변형, 복사, 경계 부드럽게, 반전, 채우기를 모두 줘요(Procreate Selections). 애플과 포토샵은 표준 되돌리기 단축키와 여러 단계 되돌리기를 기본으로 봐요(Apple HIG Undo and redo, Adobe Undo and Redo). 3D 돌려 보기는 이번에 따로 확인하지 않았어요. |
| 지어낸 이름 대신 포토샵 한국어판의 일반 도구 용어 | 맞음 | 포토샵 한국어 도움말은 선택 영역, 선택 윤곽 도구, 올가미 도구, 실행 취소 및 다시 실행, 작업 내역 패널, 빠른 마스크, 도구 포인터, 툴팁 같은 이름을 써요(Adobe KR Selection tools overview). NN/g도 아이콘과 이름은 경쟁 제품과 대상 플랫폼이 쓰는 것을 먼저 보라고 해요(NN/g Icon Usability). |
| 선택 영역은 색 채움이 아니라 개미 행렬로 표시 | 일부 | 기본 표시가 움직이는 점선인 것은 맞아요(Adobe Selection tools overview). 하지만 김프는 점선이 반쯤 선택된 경계만 보여 준다며 반투명 색 덮개(빠른 마스크)로 전체 모양을 보라고 하고(GIMP Quick Mask), 프로크리에이트는 선택 확정 뒤 바깥을 빗금으로 덮어요(Procreate Selections). 기본은 점선, 부드러운 선택은 덮개를 고를 수 있게가 근거와 맞아요. |
| 모든 도구에서 포인터가 보임 | 맞음 | 포토샵은 칠하는 도구마다 브러시 끝 크기 테두리나 십자 커서를 보여 줘요(Adobe Cursor preferences). 애플은 펜을 띄웠을 때 칠해질 크기와 색을 미리 보여 주라고 해요(Apple HIG Apple Pencil). 단, 커서에 안내 글을 붙이지는 말라고 해요(Apple HIG Pointing devices). |
| 이미지 위 동작은 마우스를 올릴 때 아이콘으로, 모서리에 작은 x | 일부 | 마우스 올릴 때 드러내는 것 자체는 애플도 허용해요. 다만 꼭 필요한 동작은 터치에서 그 자리를 누르면 보이고 길게 누르는 메뉴에도 있어야 해요(Apple HIG Pointing devices). NN/g는 마우스 올리기는 터치에서 안 된다고 해요(NN/g Tooltip Guidelines, Icon Usability). 작은 x는 보이는 크기와 별개로 누름 영역이 웹 최소 24 CSS px(중요하면 44)여야 해요(W3C 2.5.8). 지우기처럼 결과가 큰 버튼은 더 크게, 가장자리에서 떨어뜨리라는 권고도 있어요(Microsoft Targeting). |
| 변형하는 동안 미리보기가 최종 색과 조명과 같아야 함 | 맞음 (조명은 일부) | 직접 조작은 결과가 바로 보여야 하고(NN/g Direct Manipulation), 미리보기가 실제 결과와 다르면 도움이 안 된다고 해요(Apple HIG Apple Pencil). 라이트룸 "후" 화면도 고치는 즉시 바뀐 모습을 보여 줘요(Adobe Develop module basics). 3D 조명까지 같아야 한다는 문서는 찾지 못했어요. 일반 원칙에서 미뤄 본 판단이에요. |
